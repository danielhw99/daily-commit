# LeetCode 풀이 정리 규칙

## 적용 범위와 학습 원칙

- LeetCode 문제의 학습 및 `leetcode/` 아래 파일 작성·정리에 적용한다.
- 저장소 루트의 [AGENTS.md](../AGENTS.md)를 함께 따른다. 질문과 단계별 힌트로 사용자가 스스로 해결하도록 돕는다.
- LeetCode 제출 결과가 이 저장소에 자동으로 저장된다고 가정하지 않는다. 학습한 풀이와 설명을 아래 구조에 직접 파일로 기록한다.
- 파일 작성이 정답을 먼저 공개하는 수단이 되어서는 안 된다. 학습 중에는 사용자가 작성한 코드와 도출한 내용까지만 기록하고, 아직 해결하지 않은 부분은 `미해결` 또는 `학습 중`으로 표시한다.
- 문제 유형 자체가 힌트가 될 때는 사용자가 접근법을 도출한 뒤 유형을 확정하여 저장한다.

## 폴더 구조

분류 순서는 **문제 유형(알고리즘 또는 자료구조) → 난이도 → 문제**로 통일한다. 날짜 폴더는 만들지 않는다.

```text
leetcode/
  AGENTS.md
  <유형>/
    <easy|medium|hard>/
      <문제번호>-<문제-slug>/
        solution.<언어 확장자>
        README.md
```

- 유형은 풀이의 핵심 알고리즘 또는 자료구조로 정한다. 예: `array`, `hash-table`, `stack`, `queue`, `linked-list`, `tree`, `graph`, `sorting`, `binary-search`, `two-pointers`, `sliding-window`, `bfs`, `dfs`, `dynamic-programming`, `greedy`, `backtracking`.
- 여러 유형에 해당하면 실제 풀이의 핵심 유형 하나를 대표 폴더로 사용하고, 나머지는 문제 문서의 관련 유형에 기록한다. 같은 문제를 유형별로 복제하지 않는다.
- 기존 유형 폴더를 먼저 확인하고 동일한 의미의 폴더를 다른 이름으로 만들지 않는다. 새 유형은 영문 소문자와 하이픈으로 작성한다.
- 난이도는 LeetCode의 문제 난이도를 기준으로 `easy`, `medium`, `hard` 중 하나를 사용한다. 확인되지 않은 난이도를 임의로 지정하지 않는다.
- 풀이 날짜는 폴더 경로에 넣지 않고 문제의 README.md에만 기록한다. 사용자가 지정한 날짜를 우선하고, 지정하지 않았다면 기록 시점의 Asia/Seoul 날짜를 `YYYY-MM-DD`로 사용한다.
- 문제 폴더는 문제 번호와 LeetCode URL의 slug를 사용한다. 예: `1-two-sum`.
- 정보가 부족하면 사용자에게 확인한다. 빈 예시 문제나 가짜 풀이 기록을 만들지 않는다.

## 문제당 파일 구성

각 문제 폴더에는 **풀이 코드 1개와 문제 설명·해설 Markdown 1개**, 총 2개의 파일을 둔다.

### `solution.<언어 확장자>`

- 사용자가 선택한 언어를 사용한다. 별도 지정이 없으면 현재 학습 중인 언어를 따른다.
- 예: Python은 `solution.py`, Java는 `solution.java`, C++은 `solution.cpp`.
- LeetCode에서 요구하는 클래스와 메서드 형식을 유지한다.
- 사용자가 작성한 풀이를 기록하고 핵심 의도에 필요한 주석만 추가한다.
- 다른 풀이, 실패한 시도, 테스트 사례는 별도 소스 파일을 늘리지 않고 `README.md`에 정리한다.
- 미완성 코드를 임의로 완성하거나 검증하지 않은 코드를 통과한 풀이로 표시하지 않는다.

### `README.md`

아래 형식을 기준으로 한국어로 작성한다. 학습 중인 항목은 현재 확인한 내용까지만 작성한다.

```markdown
# <문제번호>. <문제 제목>

## 문제 정보

- 링크: <LeetCode 문제 URL>
- 대표 유형: <폴더에 사용한 유형>
- 관련 유형: <추가 유형 또는 없음>
- 난이도: <Easy / Medium / Hard>
- 풀이 날짜: <YYYY-MM-DD>
- 언어: <사용 언어>
- 상태: <학습 중 / 풀이 완료·제출 미확인 / Accepted 확인>

## 문제 설명

문제의 목표를 자신의 말로 요약한다.
입력, 출력, 주요 제약 조건과 예제를 기록한다.

## 접근 과정

처음 생각한 방법, 병목이나 실패 원인, 개선 과정과 핵심 관찰을 기록한다.

## 풀이 해설

사용자가 도출한 알고리즘과 자료구조의 선택 이유를 설명한다.
처리 순서와 이 방법이 정답을 보장하는 이유를 기록한다.
코드는 같은 폴더의 solution 파일을 상대 링크로 연결한다.

## 복잡도

- 시간 복잡도: <Big-O와 근거>
- 공간 복잡도: <Big-O와 근거>
- 변수 정의: <n, m 등이 의미하는 입력 크기>

## 검증과 주의점

확인한 예제, 경계 조건, 실수하기 쉬운 부분을 기록한다.
실제로 실행한 테스트 결과와 LeetCode 제출 결과를 구분한다.
실행하거나 제출하지 않았다면 미확인이라고 적는다.

## 복습

핵심 아이디어, 같은 접근을 떠올릴 수 있는 문제의 특징,
사용자가 설명한 내용과 남은 질문을 짧게 기록한다.
```

## 작성 및 갱신 절차

1. 루트의 학습 규칙에 따라 문제를 분석하고 사용자와 단계적으로 풀이한다.
2. 저장 전에 문제 번호로 기존 기록을 확인한다. 같은 문제는 기존 파일을 갱신하고 최초 풀이 날짜와 경로를 유지한다. 재풀이 날짜와 변경 내용은 기존 문서에 추가한다.
3. 유형, 난이도, 문제 번호와 slug를 확인하고 해당 경로에 두 파일을 작성한다. 풀이 날짜는 README.md에 기록한다.
4. 해설은 사용자의 실제 사고 과정과 코드에 맞춘다. 학습이 진행되면 기존 파일의 미완성 내용을 갱신한다.
5. 코드와 해설의 일치, 파일 수, 경로, 상대 링크, 복잡도 근거와 검증 상태를 확인한다.
6. 사용자에게 생성·수정한 파일 경로를 안내한다. 로컬 파일 저장과 GitHub 반영을 구분하고, 실제로 수행하지 않은 커밋·푸시를 완료했다고 말하지 않는다.
